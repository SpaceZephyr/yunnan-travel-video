# 城市总攻略视频 · 创作工作流

> 版本：v1.2（2026-11-12，加云南系列规则，见第 14 节）；v1.1（2026-11-11，补参考片拆解与镜头组件库）；v1.0（2026-11-10）
>
> 从《地理视频创作工作流》衍生，专门制作「一座城市怎么玩」的 2–3 分钟竖屏总攻略。原地理 / 徒步工作流继续独立使用，不用本流程替代。
>
> 核心产物不是景点清单，而是：**城市心智地图 + 能照着走的分片路线 + 一日 / 两日组合方案。**

---

## 0. 内容定位与默认成品

### 默认观众

第一次到这座城市的游客，计划玩 1–2 天，以公共交通和步行为主，希望少折返、少做功课。

如用户明确指定亲子、自驾、老人、深度游、美食、夜景或摄影，则替换默认画像，不要同时兼顾所有人群。

### 默认规格

- 时长：2–3 分钟，按最终配音时长走，不为了凑时长注水。
- 画幅：1080×1920，抖音 + 小红书。
- 片区：默认 3 个，可根据城市结构用 2–4 个，不强行套用「三个圈」。
- 路线：每个片区 1 条代表路线，每条 3–5 个主要站点。
- 结构：交通 → 住宿片区 → 分片游玩 → 一日 / 两日组合。
- 画面：2D 地图导览为主，实拍 / 照片解释体验，3D 只在地形或空间关系确有帮助时使用。
- 附加产物：一页 `路线卡.md`，可改写为发布正文或置顶评论；不默认做网页路书。

### 看完必须能回答

1. 这座城市可以分成哪几块玩？
2. 我从哪里进入最方便，市内主要靠什么移动？
3. 我应该住在哪个片区，为什么？
4. 每个片区从哪进、到哪出、按什么顺序走？
5. 只有一天或两天，应该怎样组合？

### 0.1 参考片拆解（抖音「小尤到处玩」香港攻略，录屏前 64 秒）
来源：`~/Downloads/ScreenRecording_11-06-2026 20-34-20_1.MP4`（1206×2622 录屏，含平台 UI）。只学结构和镜头语言，不照搬文案、钩子和画面。
| 时间 | 段落 | 画面做法 | 口播要点 |
|---|---|---|---|
| 0–10s | 钩子 + 本期模型 | 卫星底图上城市边界紫色填充 + 超大城市名；随后三块区域变绿圈 | 「景点分布其实很简单，用三个圈讲交通、住宿、景点」 |
| 10–12s | 转场判断句 | 全屏街景实拍 + 两行大字 | 「不是说走就走的城市」 |
| 12–22s | 出发前准备 | 模糊实拍背景 + 图标贴纸清单，每说一项追加一行，黄字 | 证件、现金、手机卡、充电宝/转换器、电子支付，共 5 项 |
| 22–45s | 到达交通 | 顶部常驻章节条（图标+「进出港交通」）；总图上口岸逐个落点，亮线从口岸画到市区；穿插 1–2 张实拍（大桥、巴士） | 按「多数人选的 → 次选 → 特定人群」排序，每个入口说清到哪、怎么接续、多久 |
| 43–45s | 市内交通 | 交通工具图标贴纸叠在地图上 | 只说公交、地铁、出租车三种 |
| 45–64s | 景点片区 | 先缩放到片区，黄字片区名 + 水面上巨型半透明地名（维多利亚港）；站点 pin 随口播逐个弹出，旁边弹小缩略图；最后切全屏实拍 | 片区一句定位 → 站点顺序 → 距离（约一公里）→ 具体能看到什么 |
节奏数据：约 45 字/10 秒，字幕一行 1–2 秒一换；每 3–6 秒必有一次画面变化（新 pin、新贴纸、切实拍）。准备 + 交通约占前 45 秒，在完整片里压到 25% 以内，路线段才是主体。
可学：
- 先给「几块」心智模型，再展开，全片回到同一张总图。
- 清单类信息用逐行追加的贴纸，不用口播硬念。
- 章节条常驻顶部，观众随时知道在哪一段。
- 片区镜头三层：巨型地名水印（空间）→ 片区名（定位）→ pin + 缩略图（站点）。
不学：
- 「放弃网红攻略」「看完不烧心」这类钩子，换成本片真实的省心价值。
- 交通段穷举所有口岸；按目标观众只保留 2–4 个入口。
- 字幕压在平台 UI 区，我们的字幕和贴纸避开右侧 15% 和底部 20%。

## 1. 总流程与三个用户确认点

```text
城市 / 选题 + 城市空间模型 + 大纲
        ──（用户确认①）──▶
调研 + 路线卡 + 完整口播稿
        ──（用户确认②）──▶
配音 + 地图 + 素材 + 合成 + 全片质检
        ──▶
交付待发 + 发布预览
        ──（用户确认③）──▶
发布与归档
```

### 确认①：城市、观众和空间模型

- 用户指定城市时，不必硬给 4–5 个城市；直接提交「观众画像 + 城市空间模型 + 大纲」。
- 用户让 Agent 选题时，给 4–6 个候选，每个写清：目标观众、核心钩子、片区模型、为什么现在做、素材与数据难度、和已发内容的差异。
- 未确认前，候选只在对话中完整展示；如需暂存，放 `.workbuddy/drafts/`，不得提前写入 `3 content/geo-video/选题/`。
- 确认后才按现有项目规则更新 `已确认队列.md` 和当日大纲文件，不替用户确认。

### 确认②：路线卡和口播稿

同时交付：

1. 完整口播稿；
2. 每个片区的路线卡；
3. 事实与来源清单；
4. 不确定项及取舍。

用户说「可以 / 开始做」后才进入制作。后续不擅自改稿、增删片区或更换路线；确需修改时先说明原因。

### 确认③：发布预览

发布前展示标题、正文、话题、封面和待发布平台，得到明确同意后才上传或提交。

用户确认口播稿后，不默认出样片；地图静帧、联系表和质检图属于内部检查，不等于增加用户确认关卡。

## 2. 第一步：建立城市空间模型

先画骨架，后写稿。禁止先搜集几十个景点，再按编号串成口播。

### 2.1 必做的四层结构

1. **入口层**：机场、火车站、口岸、码头、主要高速入口，默认保留 2–4 个真正适合目标观众的入口。
2. **交通层**：1–2 条主要交通轴或走廊，解释入口与主要游玩片区怎么连接。
3. **片区层**：按真实空间与游玩逻辑划分 2–4 个片区，每片用一个固定颜色。
4. **路线层**：每片一条可执行路线，最后能组合成一日 / 两日安排。

### 2.2 片区不是行政区的机械复制

可以按以下方式划分，但必须有空间依据：

- 老城 / 新城、山上 / 山下、江两岸、海湾两侧；
- 历史街区、城市地标、本地生活、自然户外；
- 同一条地铁 / 步道 / 海岸线串起来的相邻站点。

不要只因为行政区方便就分区，也不要把需要长时间跨城的点硬塞进同一条步行路线。

### 2.3 空间模型完成标准

- 一张总图上能看懂入口、交通轴、片区和路线。
- 每个片区有一句明确的「为什么值得玩」。
- 每个片区有固定颜色，后续总览、住宿、路线和回顾保持一致。
- 一日 / 两日组合不产生明显折返，不把闭馆、夜景、夜市放在错误时段。
- 如果无法用一句话解释城市骨架，就继续收资料，不进入写稿。

## 3. 第二步：调研与路线卡

### 3.1 来源优先级

1. 官方：出入境、景区预约、开放时间、票价、交通运营、临时关闭与限流。
2. 地图与路线工具：POI 坐标、站点出口、实际路线距离和预计时间。
3. 场馆 / 交通运营方公告：班次、出入口、换乘、停运和特殊日期安排。
4. 可靠的现场资料与图片：核对实际环境、景观和体验。
5. UGC 只作体验线索，不单独支撑政策、价格、班次和安全结论。

每条动态信息记录 `来源 + 查询日期`。找不到可靠出处就不写具体数字；来源冲突时用保守表述，并告诉用户冲突在哪里。

### 3.2 交通调研

- 入境 / 到达方式按出发地做取舍，不穷举所有可能。
- 每种保留的到达方式写清：适合谁、到哪里、怎样接续、约多久、主要优缺点。
- 市内交通只讲游客真正会用到的 2–4 种，以及支付、换乘或末班车等关键限制。
- 实际路线时间不能用直线距离替代；步行、公交、轨交和驾车分别标注口径。
- 境外不套用高德数据；改用核实过的坐标、OSM、官方交通与可靠地图来源。

### 3.3 住宿片区调研

默认推荐住宿「片区」，不推荐具体酒店。

每个候选住宿片区只回答：

- 适合哪类游客；
- 到主要游玩区和交通枢纽是否方便；
- 晚上是否方便吃饭、返程；
- 有什么明确缺点，例如贵、吵、坡多、离景点远。

价格、开业状态、具体酒店评价容易变化，未实时核实不要写。若用户要具体酒店，另做专项调研，不塞进城市总攻略。

### 3.4 每条路线一张卡

```text
路线名 / 所属片区
适合谁：
为什么走这条：
起点与进入方式：
终点与离开方式：
主要站点顺序：
各段交通方式与实际路线时间：
建议总时长：
最佳开始时间：
门票、预约、开放限制：
吃饭、休息、补给：
雨天 / 高温 / 体力不足替代：
实拍素材需求：
事实来源与查询日期：
示意部分（如有）：
```

### 3.5 路线合理性检查

- 坐标逐一核对到正确 POI，不接受只解析到城市中心或同名地点。
- 站名、出口、入口和出口方向要与实际路线一致。
- 路线顺序尽量顺路；明显折返必须说明为什么值得。
- 核对第一站开门时间、最后一站闭馆 / 末班交通，以及夜景、夜市、日落等时间约束。
- 给一条简化或退出方案，不默认每个人都走完全程。
- 手描线、OSM 推测线、规划路线和真实 GPS 轨迹必须明确区分。

完成标准：路线卡没有空着的关键事实；未核实项已显著标记，没有混进定稿。

## 4. 第三步：写城市总攻略口播

### 4.1 默认章节顺序

1. **省心钩子**：告诉观众这期如何减少决策，不空喊「史上最全」。
2. **城市分圈**：先给城市总图和空间模型。
3. **出发前准备**：只讲这座城市特有的 3–6 项，删掉无差别常识。
4. **到达与市内交通**：先回答怎么到，再回答到了怎么移动。
5. **住宿片区**：按游客类型给取舍，不报酒店流水账。
6. **分片路线**：本片的正文，占全片约 45%–55%。
7. **一日 / 两日组合**：把路线重新装进行程，不再新增景点。
8. **总图回顾与提醒**：回看同一张地图，给少量关键提醒和收藏理由。

一日游且明确不涉及过夜时，住宿可以压缩或省略，但必须在确认大纲时说明。

### 4.2 每个片区的表达顺序

```text
为什么玩这片 → 从哪里进 → 按什么顺序走 → 各站具体看什么 → 约多久 → 什么时间合适 → 从哪里离开
```

不必每个站都重复完整模板，但入口、顺序、核心体验和离开方式不能丢。

### 4.3 文风

- 用「你」帮助观众做选择，用「我更推荐」表达明确取舍。
- 一句解决一个问题，短句推进；允许自然长句，但不要一句塞四五个信息点。
- 景观要具体：站在哪里、能看到什么、什么时段最好，而不是「很美、很出片、值得打卡」。
- 不机械重复「第一条、第二条、第三条」，用空间和行程衔接。
- 不照搬参考片的「放弃所有网红攻略」，钩子要落到本片真正提供的省心价值。
- 少用「必去、天花板、一期讲透、说走就走」，不编造亲身体验。

### 4.4 篇幅

- 默认 20–28 句、2–3 分钟（约 100–110 字/10 秒的口播密度下，全稿 900–1300 字）。
- 交通 + 住宿不宜挤占一半篇幅；分片路线必须是主体。
- 内容太长时优先减少片区、交通分支和泛化提醒，不牺牲路线的可执行性。
- 数字原稿用汉字供 TTS，字幕通过 `SHOW` 表显示阿拉伯数字。

### 4.5 交稿时附带

- 片区 / 路线速览表；
- 事实与来源清单；
- 动态信息查询日期；
- 示意路线、推测时间和素材不确定项；
- 需要用户拍板的取舍。

## 5. 工程与单一数据源

### 5.1 模板来源

首个城市项目优先参考 `~/Movies/hk-citywalk` 的地图、实拍对齐和发布流程，同时对比 `~/Movies/sz-kunpeng` 中更新的通用构建修复。

不要整目录复制历史项目及成片。首个项目先抽离一个干净的 `~/Movies/city-guide-template`，只保留代码、字体、必要配置和空白目录；后续从模板创建项目。

地形占比高的城市再参考 `gz-sz-peaks`，不把徒步项目的「每个对象都 3D 飞越」照搬到城市导览。

### 5.2 项目结构

```text
~/Movies/<city-guide>/
  city.json              城市、片区、入口、住宿、路线、来源的唯一主数据
  lines.json             用户确认的口播稿，一句一个字符串
  script.md              口播 + 片区路线速览 + 事实说明
  route_cards.md         可直接阅读的路线卡
  route_audit.md         路线合理性和动态信息验收记录
  tts_alt/lines.json     TTS 同音字稿
  ref.wav                克隆参考音
  voice/sNN.wav          每句最终配音
  data/                  坐标、路线与地图工具原始结果
  research/              调研、来源与素材候选
  src/                   核实并记录授权的照片 / 视频
  specs_city.py          城市总览、交通、住宿、片区路线镜头
  specs3d.py             可选，仅在确有必要时存在
  render_q.sh            地图 / 3D 渲染
  build.py               对齐、字幕、贴纸、拼接、混音
  cover.py               三版封面
  footage_audit.md       镜头、关键词、地点与授权核对
  pub/                   封面、素材来源与发布资料
  qc/                    静帧、联系表和全片质检结果
```

### 5.3 `city.json` 是最上游，不是事后补写的说明

推荐字段：

```jsonc
{
  "city": "",
  "audience": { "days": 2, "mode": "public_transport", "preference": "first_visit" },
  "updated_at": "YYYY-MM-DD",
  "entrances": [],
  "transport_axes": [],
  "zones": [
    { "id": "", "name": "", "color": "", "why": "", "stay": "" }
  ],
  "preparation": [],
  "arrival_options": [],
  "local_transport": [],
  "routes": [
    {
      "id": "",
      "zone_id": "",
      "start": {},
      "end": {},
      "mode": "walking",
      "duration": "",
      "best_start": "",
      "stops": [
        { "name": "", "coord": [], "coord_system": "", "say": 0, "at": "", "facts": [] }
      ],
      "is_schematic": false
    }
  ],
  "itinerary": [],
  "facts": [
    { "claim": "", "source": "", "publisher": "", "checked_at": "", "note": "" }
  ]
}
```

规则：

- `say` 在用户定稿后绑定句序；`at` 绑定画面出现的关键词。
- 坐标必须显式记录坐标系，不能把 WGS-84 和 GCJ-02 混用。
- 片区颜色只定义一次，所有地图镜头从这里读取。
- `lines.json` 负责配音文本，`city.json` 负责空间、路线和事实；不要同时在多个 Python 文件里手改同一组站点。
- `route_cards.md`、地图 spec、剪辑表和发布路线摘要尽量从 `city.json` 生成。

## 6. 配音与 ASR

复用原地理工作流的百炼克隆配音、`tts_alt` 同音字稿和 ASR 检查，不换音色、不打印 Key。

重点增加城市内容的读音检查：

- 地铁站、口岸、码头、道路、街巷和场馆专名；
- A2 / D2 等出口字母与数字；
- 英文地名、商圈名、线路名；
- 多音字、粤语地名和本地习惯读法。

`tts_alt` 只能改变读音，不改变原稿语义；字幕始终显示 `lines.json` 原文。

完成标准：每句配音齐全，无漏字、错字和词中间异常停顿，重点专名通过 ASR 或人工复核。

## 7. 地图与视觉设计

### 7.1 地图是叙事主线，不是片头装饰

| 段落 | 默认镜头 | 必须让观众看懂的内容 |
|---|---|---|
| 开场 | `region / overview / title` | 城市在哪里，本期用什么模型讲 |
| 城市分圈 | `region + view + pins` | 各片区位置、名称和固定颜色 |
| 到达交通 | `route / flight / pins` | 出发地、入口、目的地和接续关系 |
| 市内交通 | `view / route` | 主要交通轴与片区连接，不画成线路大全 |
| 住宿片区 | `region / pins / view` | 住在哪里，和游玩区、交通枢纽有什么关系 |
| 分片路线 | `route + pins + 地图锚点照片` | 从哪进、站点顺序、现在讲哪一站、从哪出 |
| 一日 / 两日 | `overview + 行程卡` | 每天走哪几片，怎样少折返 |
| 收尾 | `overview` | 回到同一套颜色和总图，形成记忆 |

### 7.2 2D 与 3D 的选择

- 街道、地铁、商圈、步行路线：优先 `amap` / `amap-journal` 或核实过的卫星底图。
- 境外：使用 `satellite-world` 等适用底图与核实坐标，不依赖高德的境外路线规划。
- 山城、海岛、明显高差或天际线关系：可用 `map-3d` 辅助解释。
- 不要为了每条路线都有 3D 而做 3D，也不要用 3D 飞越代替真实导航。

### 7.3 视觉规则

- 同一屏标签宁少勿多，读不清就拆镜或延后到对应站点出现。
- 关键字避开右侧平台 UI 和底部字幕安全区。
- 照片优先锚在正在讲解的站点旁；需要展示体验时再切全屏实拍。
- 地图锚点照片和全屏实拍都必须在旁白说到对应地点时出现。
- 旅行照片充足且用户明确要个人 vlog 时，才考虑 `travel-vlog` 卡通小人；城市总攻略默认不用。
- 地图、照片和数据的署名按各自许可保留，不为了画面干净删除必要来源。

### 7.4 渲染检查

复用 map-motion 的编译、静帧和自动质检：

1. 逐行核对地名解析结果，错误时换更具体的名称或直接写坐标。
2. 每个镜头至少看中段和结尾，检查路线、文字裁切、标签互压和色块。
3. 区域颜色、路线方向和站点顺序与 `city.json` 一致。
4. 3D 段除静帧外抽一小段连续画面，检查黑块、海面、远处地形和跳变。

## 8. 实景素材与对齐

沿用原工作流的素材与授权标准：

- 素材必须真的是旁白正在讲的那个地点；对不上就继续找，或用地图解释，不硬塞通用城市图。
- Wikimedia Commons 记录文件页、作者、许可和链接；其他素材同样记录来源和使用条件。
- 地点不确定的素材只能作泛指画面，不加具体地名字幕。
- 每个素材使用 `at="关键词"` 对齐，不用拍脑袋秒数。
- 照片整张显示，背景可模糊填充，只做缓慢推近，不平移、不裁掉关键内容。
- 全屏照片通常保留约 2.5–4 秒；关键词过近时减少图片，不快速闪切。
- 不用尾帧冻结撑时长；保持原有 `freezedetect` 验收标准。
- `footage_audit.md` 写清每句、每个关键词、每个素材和授权之间的对应关系。

## 9. 合成与路线质检

### 9.1 剪辑顺序

```text
开场城市模型
→ 准备与到达
→ 市内交通与住宿片区
→ 片区 A：总图 → 路线 → 站点实拍 → 离开方式
→ 片区 B：同上，但避免机械重复相同转场
→ 片区 C
→ 一日 / 两日组合
→ 总图回顾
```

地图负责空间连续性，实拍负责体验，贴纸只突出决策信息。不要让每种信息都同时挤在一张图上。

### 9.2 `route_audit.md` 是独立验收文件

逐条记录：

- POI 名称、坐标和坐标系是否核对；
- 起点、终点和站点顺序是否与实际路线一致；
- 距离 / 时间来自哪种路线规划，查询日期是什么；
- 是否存在明显折返，是否有合理原因；
- 开放、预约、末班交通和最佳时段是否冲突；
- 简化路线、退出方式和雨天替代是否成立；
- 哪些线为示意，画面和文案是否都明确说明；
- 发布前需要再次核实的动态信息。

自动脚本只能辅助检查缺字段、坐标异常和路线距离，不能把「脚本跑过」当作事实正确。关键路线与政策仍需人工看来源。

### 9.3 全片技术质检

继续执行原标准：

- 1080×1920、时长、音轨完整；
- 响度约 -16 LUFS；
- ASR 与重点专名通过；
- `freezedetect` 无违规冻结段；
- 每 6–8 秒抽帧联系表，检查画面、字幕、贴纸、素材缺失和出框；
- 按入口、路线转折、站名、票价、开放时间等关键词时刻抽帧；
- 检查片区颜色、路线顺序和住宿 / 行程回顾是否前后一致。
